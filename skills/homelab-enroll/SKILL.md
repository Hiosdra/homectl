---
name: homelab-enroll
description: Adopt existing SSH/local machines or provision cloud-init VMs on Proxmox and enroll them through homectl. Use when adding a host or creating a homelab VM with requested resources and access tier.
---

1. Read README enrollment/provisioning guidance. Use existing remote users. Resolve the requested access tier and purpose from the user's request; preserve an explicitly selected full tier. Avoid design questions when the request already provides enough information.
2. ADOPT: prepare a secret-free host JSON using examples/host.example.json and validate with `homectl enroll <name> --file <path> --dry-run --json`. Configure auth as a key-agent backend or Agent Access item ID. The agent never receives the password/private key. Establish initial fingerprint trust in known_hosts using a trusted source; the user may perform initial authentication privately once.
3. Run enroll to test connectivity/OS and write inventory plus SSH alias. Use `--configure-sudo` only when requested and supported by existing noninteractive sudo/bootstrap access. Full renders NOPASSWD: ALL for the existing user; sudo-approved renders literal exact argv rules. If initial sudo needs a password, have the user apply the printed policy through a private trusted terminal rather than exposing that password. Inspect pre-existing privileges: adding a limited sudoers rule does not remove broader grants. Such cleanup is a separate concrete, explicitly approved config change.
4. PROVISION: prepare a VM JSON from examples/vm.example.json. Specify template, VMID, static IPv4, bridge/gateway, template user, SSH public key, CPU/RAM/disk, tier and optional docker/bun recipes. Never supply a private key or API secret. Use a prepared cloud-init template with the existing account, cloud-init drive and appropriate privilege policy. New image/template import and automatic DHCP discovery are currently deferred; explain these boundaries.
5. Run `homectl provision --file <path> --dry-run --json`, review resources/identity/network and then apply the user's requested creation. The CLI uses the Proxmox API through token injection, waits for tasks/SSH/cloud-init, enrolls and verifies optional software. Make initial VM host-key trust possible through the console/fingerprint out of band; a timed-out first run can be resumed with the same plan.
6. Reuse the same plan to resume. A VMID/name conflict, changed request, uncertain clone or failed task requires inspection, never deletion/recreation or an automatic destructive rollback. Do not erase the provisioning journal to force reuse of a VMID. Deleting a VM follows the day-to-day skill's exact destructive-operation confirmation flow.
7. Run `homectl inspect <name> --json` and `homectl doctor <name> --json`; report whether auth, tier and services are verified. For sudo-approved, actual hard enforcement requires administrator review of all sudoers/groups/polkit rules; declared enforcement is not proof.
8. Install only the requested software. Do not install Codex or Claude Code on the new machine unless separately requested. There is no fleet of new coding agents.

Every deletion, reset, format or destructive config replacement requires explicit human confirmation of the concrete targets and effects, even with full/root. Normal privileged non-destructive actions use the native approval flow without custom double confirmation. Preserve provider/host secrets on the agent host and credential provider; never send them through a remote-control client.
